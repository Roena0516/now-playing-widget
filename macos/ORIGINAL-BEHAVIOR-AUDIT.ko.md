# 원본 동작과 macOS 가사 누락 분석

분석 기준: Windows 원본 `e00507c`의 `src/` 전체 흐름, 2026-10-18 KST의 로컬 Pear API 응답, LRCLIB 실제 조회 응답, 실행 중인 macOS 앱의 `lyrics.log`, 설치된 YouTube Music 앱의 YTMusic 제공자 코드. 음표 메뉴의 가사 상태와 로그를 근거로 수신 실패와 표시 실패를 구분한다.

## 원본의 데이터 흐름

1. `PearClient.cs`가 로컬 `/auth/{id}`에서 연결 토큰을 받고 WebSocket의 `PLAYER_INFO`, `VIDEO_CHANGED`, `PLAYER_STATE_CHANGED`, `POSITION_CHANGED`를 처리한다. 여기서 받는 것은 곡 정보와 재생 상태이며 음악 앱에 보이는 가사 자체는 아니다.
2. `TrayApp.EnsureLyrics`가 `videoId|title` 변경을 감지하면 이전 검색을 취소하고 이전 가사 창을 숨긴 뒤, LRCLIB를 별도로 검색한다. 같은 곡은 캐시를 사용한다.
3. `LyricsProvider.Find`의 정확 조회는 아티스트·제목·앨범·반올림한 곡 길이를 사용한다. 싱크 가사가 없고 연주곡도 아니면 검색으로 넘어간다.
4. 아티스트·제목·선택적 앨범으로 검색하고, 이후 대체 제목+첫 아티스트, 정리한 제목+첫 아티스트, 정리한 대체 제목의 자유 검색을 중복 제거해 실행한다.
5. 아티스트는 공동 아티스트와 괄호 속 별칭을 분리하고 Jaro-Winkler 유사도 `> 0.9`로 비교한다. 아티스트가 맞지 않으면 곡 태그도 비교한다. 길이 차이가 15초 이내인 후보에서 가장 가까운 싱크 가사를 우선한다.
6. 그래도 없으면 제목과 대체 제목을 NFKC·소문자·문자/숫자만 남기는 방식으로 정규화한다. 아티스트가 달라도 정규화 제목이 같고 길이 차이가 3초 이내인 싱크 가사를 선택한다.
7. 성공·연주곡·검색 결과 없음은 캐시한다. HTTP 오류/타임아웃은 캐시하지 않고, 요청 완료 후 각각 3초·10초·30초를 기다리며 최대 4번 시도한다. 각 HTTP 요청 제한은 20초이다. 따라서 전체 검색은 단순히 43초에 끝나는 구조가 아니다.
8. 메뉴의 가사 다시 찾기는 해당 곡 캐시를 지우고 다시 검색한다. 진단은 `error.log`와 트레이 상태에 기록한다.

## 원본이 가사 창을 표시하는 조건

`TrayApp.TickLyrics`는 가사 표시가 켜져 있고, 검색 결과에 파싱된 시간표가 있으며, 현재 곡 정보가 있을 때만 가사 창을 만든다. `plainLyrics`만 있는 곡, 검색 실패, 검색 중, 연주곡은 가사 창이 없다. 일반 가사에서 자동으로 시간을 추정하거나, 음악 앱의 가사 탭/영상 자막을 읽는 구현은 없다.

가사 창과 곡 카드는 독립된 두 창이다. 원본 기본값은 곡 카드를 6초만 표시하고 가사는 유지하는 것이다. 일시정지/재개 시 곡 카드가 다시 나타난다. 가사는 로컬 재생 시계+기본 300ms 보정으로 현재 줄을 계산하고, 약 100ms마다 상태를 확인한다. 줄 전환은 460ms ease-out, 큰 탐색 이동은 260ms로 움직이며, 현재 줄 옆에만 3px 강조선이 있다. 간주·첫 가사 이전에는 `♪`를 사용한다.

원본 위치는 전체 모니터 경계 기준으로 왼쪽 40px·아래 140px, Windows DPI 배율 적용이다. 가사가 있을 때 아래쪽 여백에는 가사 창이 붙고 곡 카드는 10px 위에 놓인다. 상단에서는 곡 카드가 여백에 붙고 가사가 아래에 놓인다. 사용자의 추가 요청에 따라 최종 macOS 버전은 Dock/메뉴 막대를 제외한 영역의 24pt 여백으로 의도적으로 조정했다.

LRCLIB의 HTTP 503은 관찰한 개별 요청의 실패다. LRCLIB 전체 서비스가 계속 중단됐다는 의미도, YouTube Music 앱의 가사가 함께 중단돼야 한다는 의미도 아니다. 설치된 음악 앱은 YTMusic/LRCLib/MusixMatch/Genius 제공자를 지원하지만 이 위젯의 초기 구현은 LRCLIB만 사용했다. 따라서 두 앱의 가사 가용성은 달랐다.

또한 초기 macOS 검색 조건에서도 위 SAWTOWNE 곡의 후보 1건은 조건을 통과한다. 제목 기호 차이만으로 당시 미표시 원인을 단정할 수 없다. 실제 실패 로그와 현재 실행 중인 빌드의 진단이 필요하다.

## 포트의 누락과 수정

- 초기 포트에는 원본의 대체 제목, 태그, 제목 정리, 아티스트 별칭·유사도, 다단계 자유 검색과 캐시가 빠져 있었다. 이를 옮겼다.
- LRC의 `[mm:ss:ff]`, 밀리초 3자리 처리, 마지막 offset 적용, 줄 앞 타임스탬프만 파싱하는 규칙을 원본과 맞췄다.
- 검색 중/일반 가사만 있음/연주곡/미발견/서버 오류를 구분하고 실제 조회 로그를 추가했다.
- 한 LRCLIB 요청이 실패해도 다른 검색 방식은 시도한다. 적합한 싱크 가사를 찾으면 앞선 오류와 관계없이 사용한다. 결과가 없고 요청 오류가 남아 있으면 정상적인 미발견으로 캐시하지 않고 재시도한다. 이는 원본의 첫 오류에서 중단되는 동작을 개선한 부분이다.
- YTMusic 우선, LRCLIB 후순위로 연결했다. Google 직접 browse를 먼저 시도하며, 제공되지 않으면 설치된 Pear의 YTMusic 제공자가 사용하는 가사 프록시를 이용한다. 외부 요청에는 Google 계정 쿠키·로컬 Pear 토큰을 전달하지 않는다.
- Pear REST API의 `/doc`를 확인한 결과 설치된 버전에는 가사 엔드포인트가 없었다. 새 경로는 음악 앱의 가사 탭을 REST로 전달받는 기능이 아니라 YTMusic 제공자 경로로 별도 조회하는 것이다. 계정에서 보이는 가사와 항상 같다고 보장할 수 없고, 내부 응답 변경·지역·프록시 장애 시 LRCLIB로 넘어간다.

## 검증 범위

네이티브 빌드와 서명 검사, LRC·설정·배치 테스트, 가사 검색 순서/유사도/길이/캐시/503 테스트, YTMusic 응답 파싱/프록시 전환/인증정보 분리 테스트를 통과했다. 실제 LRCLIB 응답의 69줄과 YTMusic 응답의 61줄을 Swift 코드로 파싱했다. 기존 실행 앱의 LRCLIB 69줄 수신 로그도 확인했다. 최종 YTMusic 연동 빌드의 GUI 표시 확인은 앱 재실행 후 로그로 별도 확인해야 한다.

음악 앱의 별도 API 요청 로그 파일은 발견하지 못했다. macOS 통합 로그 조회는 이 실행 세션의 샌드박스에서 차단됐다. Chromium의 LevelDB 로그를 API 로그로 간주하지 않았다.
