# 원본 동작과 macOS 가사 누락 분석

이 문서는 macOS 버전에서 가사가 표시되지 않던 원인을 분석한 기록입니다. 분석에 사용한 자료는 다음과 같습니다: Windows 원본 `e00507c`의 `src/` 전체 흐름, 2026-10-18 KST에 받은 로컬 Pear API 응답, LRCLIB에 실제로 조회한 응답, 실행 중이던 macOS 앱의 `lyrics.log`, 설치된 YouTube Music 앱에 들어 있는 YTMusic 제공자 코드. 가사를 받지 못한 경우와 받았지만 표시하지 못한 경우는 음표 메뉴의 가사 상태와 로그를 근거로 구분했습니다.

## 원본의 데이터 흐름

1. `PearClient.cs`는 로컬 `/auth/{id}`에서 연결 토큰을 받고, WebSocket으로 들어오는 `PLAYER_INFO`, `VIDEO_CHANGED`, `PLAYER_STATE_CHANGED`, `POSITION_CHANGED` 메시지를 처리합니다. 이 메시지로 받는 정보는 곡 정보와 재생 상태이며, 음악 앱에 표시되는 가사 자체는 들어 있지 않습니다.
2. `TrayApp.EnsureLyrics`는 `videoId|title`이 바뀐 것을 감지하면 이전 검색을 취소하고 이전 가사 창을 숨긴 뒤, LRCLIB에서 가사를 따로 검색합니다. 같은 곡은 캐시된 결과를 사용합니다.
3. `LyricsProvider.Find`의 정확 조회는 아티스트, 제목, 앨범, 반올림한 곡 길이를 사용합니다. 싱크 가사가 없고 연주곡도 아니면 검색 단계로 넘어갑니다.
4. 검색 단계에서는 먼저 아티스트, 제목, 그리고 (있다면) 앨범으로 검색합니다. 그다음 "대체 제목 + 첫 번째 아티스트", "정리한 제목 + 첫 번째 아티스트", "정리한 대체 제목"으로 자유 검색을 실행하며, 중복된 검색어는 한 번만 보냅니다.
5. 아티스트 이름은 공동 아티스트와 괄호 안의 별칭으로 나눈 뒤, Jaro-Winkler 유사도가 `0.9`보다 큰지 비교합니다. 아티스트가 맞지 않으면 곡의 태그도 비교합니다. 길이 차이가 15초 이내인 후보 중에서 길이가 가장 가까운 싱크 가사를 우선합니다.
6. 그래도 결과가 없으면 제목과 대체 제목을 정규화합니다(NFKC 정규화, 소문자 변환, 문자와 숫자만 남기기). 아티스트가 다르더라도 정규화한 제목이 같고 길이 차이가 3초 이내인 싱크 가사를 선택합니다.
7. 찾은 결과, 연주곡, 검색 결과 없음은 캐시합니다. HTTP 오류와 타임아웃은 캐시하지 않으며, 요청이 끝난 뒤 각각 3초, 10초, 30초를 기다리면서 최대 4번 시도합니다. 각 HTTP 요청의 제한 시간은 20초입니다. 따라서 전체 검색이 단순히 43초 안에 끝나는 구조는 아닙니다.
8. 메뉴의 "가사 다시 찾기"는 해당 곡의 캐시를 지우고 다시 검색합니다. 진단 정보는 `error.log`와 트레이 상태에 기록합니다.

## 원본이 가사 창을 표시하는 조건

`TrayApp.TickLyrics`는 가사 표시가 켜져 있고, 검색 결과에 파싱된 시간 정보가 있으며, 현재 곡 정보가 있을 때만 가사 창을 만듭니다. `plainLyrics`만 있는 곡, 검색에 실패한 곡, 검색 중인 곡, 연주곡에는 가사 창이 표시되지 않습니다. 일반 가사에서 시간 정보를 자동으로 추정하거나, 음악 앱의 가사 탭이나 영상 자막을 읽는 기능은 구현되어 있지 않습니다.

가사 창과 곡 카드는 서로 독립된 두 개의 창입니다. 원본의 기본 설정은 곡 카드를 6초 동안만 표시하고 가사 창은 계속 유지하는 것입니다. 일시정지하거나 다시 재생하면 곡 카드가 다시 나타납니다. 현재 가사 줄은 로컬 재생 시계에 기본 보정값 300ms를 더해서 계산하며, 약 100ms마다 상태를 확인합니다. 줄이 바뀔 때는 460ms 동안 ease-out으로 움직이고, 탐색으로 크게 이동할 때는 260ms 동안 움직입니다. 3px 강조선은 현재 줄 옆에만 표시됩니다. 간주 구간과 첫 가사가 나오기 전에는 `♪`를 표시합니다.

원본의 기본 위치는 모니터 전체 영역을 기준으로 왼쪽 40px, 아래쪽 140px이며, Windows의 DPI 배율을 적용합니다. 가사가 있으면 가사 창이 아래쪽 여백에 붙고, 곡 카드는 가사 창보다 10px 위에 놓입니다. 화면 위쪽에 배치하면 곡 카드가 여백에 붙고 가사 창이 그 아래에 놓입니다. 최종 macOS 버전은 사용자의 추가 요청에 따라 Dock과 메뉴 막대를 제외한 영역을 기준으로 24pt 여백을 사용하도록 의도적으로 조정했습니다.

관찰된 LRCLIB의 HTTP 503은 개별 요청이 실패한 것입니다. 이것은 LRCLIB 서비스 전체가 계속 중단되었다는 뜻이 아니며, YouTube Music 앱의 가사도 함께 표시되지 않아야 한다는 뜻도 아닙니다. 설치된 음악 앱은 YTMusic, LRCLib, MusixMatch, Genius 제공자를 지원하지만, 이 위젯의 초기 구현은 LRCLIB만 사용했습니다. 따라서 두 앱에서 가사를 받을 수 있는 범위가 서로 달랐습니다.

또한 초기 macOS 버전의 검색 조건에서도 위 SAWTOWNE 곡의 후보 1건은 조건을 통과합니다. 따라서 제목에 들어 있는 기호의 차이만으로는 당시 가사가 표시되지 않은 원인을 단정할 수 없습니다. 원인을 확정하려면 실제로 실패했을 때의 로그와, 실행 중인 빌드의 진단 정보가 필요합니다.

## macOS 버전에서 빠졌던 부분과 수정 내용

- 초기 macOS 버전에는 원본에 있는 대체 제목, 태그, 제목 정리, 아티스트 별칭과 유사도 비교, 여러 단계의 자유 검색, 캐시가 빠져 있었습니다. 이 기능들을 옮겼습니다.
- LRC 파서에서 `[mm:ss:ff]` 형식, 밀리초 세 자리 처리, 마지막 offset 태그 적용, 줄 앞에 있는 타임스탬프만 파싱하는 규칙을 원본과 같게 맞췄습니다.
- 검색 중, 일반 가사만 있음, 연주곡, 찾지 못함, 서버 오류를 서로 구분해서 표시하고, 실제 조회 과정을 기록하는 로그를 추가했습니다.
- LRCLIB 요청 하나가 실패해도 다른 검색 방법을 계속 시도합니다. 적합한 싱크 가사를 찾으면 앞에서 발생한 오류와 관계없이 그 가사를 사용합니다. 결과가 없고 요청 오류가 남아 있으면, 정상적으로 "찾지 못함"인 경우와 달리 캐시하지 않고 다시 시도합니다. 이 부분은 첫 오류에서 검색을 중단하던 원본의 동작을 개선한 것입니다.
- YTMusic을 먼저 사용하고 LRCLIB를 나중에 사용하도록 연결했습니다. 이때는 Google에 직접 browse를 먼저 시도하고, 가사를 받지 못하면 설치된 Pear의 YTMusic 제공자가 사용하는 가사 프록시를 이용했습니다. 외부 요청에는 Google 계정 쿠키나 로컬 Pear 토큰을 전달하지 않습니다.
- Pear REST API의 `/doc`를 확인한 결과, 설치된 버전에는 가사를 제공하는 엔드포인트가 없었습니다. 따라서 새 경로는 음악 앱의 가사 탭을 REST로 전달받는 기능이 아니라, YTMusic 제공자와 같은 경로로 가사를 따로 조회하는 기능입니다. 이 방식으로 받은 가사가 사용자 계정에서 보이는 가사와 항상 같다고 보장할 수는 없습니다. 내부 응답 형식이 바뀌거나, 지역 제한이 있거나, 프록시에 장애가 생기면 LRCLIB로 넘어갑니다.

## 검증 범위

네이티브 빌드와 서명 검사, LRC·설정·배치 테스트, 가사 검색 순서·유사도·길이·캐시·503 처리 테스트, YTMusic 응답 파싱·프록시 전환·인증 정보 분리 테스트를 통과했습니다. 실제 LRCLIB 응답의 69줄과 YTMusic 응답의 61줄을 Swift 코드로 파싱하는 것도 확인했습니다. 이전에 실행 중이던 앱이 LRCLIB에서 69줄을 받은 로그도 확인했습니다. 다만 YTMusic을 연동한 최종 빌드가 화면에 가사를 표시하는지는, 앱을 다시 실행한 뒤 로그로 따로 확인해야 합니다.

음악 앱이 남기는 별도의 API 요청 로그 파일은 찾지 못했습니다. macOS 통합 로그는 분석을 실행한 세션의 샌드박스에서 조회가 차단되었습니다. Chromium의 LevelDB 로그는 API 요청 로그로 간주하지 않았습니다.

## Windows 1.4.4 후속 반영

원격 저장소의 `e3a4710`, `a9ac830` 업데이트를 macOS 버전에도 반영했습니다. LRCLIB가 혼잡 응답(429/502/503/504)을 보내면 2초 뒤에 같은 요청을 한 번 다시 보내고, `Retry-After`에 적힌 초 단위 값은 2초에서 10초 사이로 제한해서 따릅니다. 혼잡이 계속되면 그 조회를 끝내고, 15초 뒤와 45초 뒤에 전체 조회를 다시 시도합니다. 앞에서 분석한 3초·10초·30초 간격의 재시도와, 혼잡한 상태에서 다른 검색을 연달아 시도하던 동작은 이 빌드부터 바뀌었습니다. 영상 제목의 장식과 커버 표기를 정리하는 기능, `및`과 `と`로 이어진 공동 아티스트를 나누는 기능, 수동으로 다시 검색할 때 진행 상황과 결과를 카드로 보여주는 기능도 추가했습니다. 위에 적은 실제 응답 기록은 당시에 관찰한 결과이므로 그대로 둡니다.

## Windows 1.5.0 반영

Windows 1.5.0에서 가사를 찾는 순서를 그대로 옮겼습니다. 따라서 위 기록 중 "Google에 직접 browse를 먼저 시도"한다는 내용은 더 이상 맞지 않습니다. 로그인하지 않은 상태로 직접 browse하면 항상 "Lyrics not available at this time." 응답을 받기 때문에, 지금은 Windows 버전과 마찬가지로 중계 서버만 사용합니다. 새로 추가된 기능은 MV의 공식 음원 찾기, 커버곡의 원곡 가사 사용(설명란 링크를 먼저 확인하고, 링크가 없으면 제목으로 원곡을 추정), 다음 곡 가사 미리 찾기, 중계 서버 서킷 브레이커, LRCLIB 정확 조회에서 대체 제목 사용입니다. 커버곡 해석 기능이 같은 입력에 대해 C# 코드와 같은 결과를 내는지는 `--lyrics-tests`에서 확인합니다.
